# 008 可靠性工程

## 本课要点

生产环境必须解决的问题：

- **幂等性**：同样的请求重复执行不产生副作用
- **错误处理**：超时、重试、降级
- **输出校验**：JSON Schema 校验 LLM 输出
- **循环上限**：最大轮次限制，防止无限循环烧钱
- **成本控制**：模型分级路由、缓存、流式输出

## 各项详解

### 幂等性
- 工具可能被重复调用（网络超时后重试）
- 设计：带 idempotency key，或先查状态再执行

### 输出校验
```python
# LLM 输出的 JSON 不一定合法，必须校验+修复
try:
    data = json.loads(raw)
    validated = MySchema.validate(data)
except ValidationError as e:
    messages.append({"role": "user", f"输出不合法：{e}，请修正"})
    continue  # 让 LLM 重试
```

### 循环上限
```python
for turn in range(max_turns):  # 默认 10-20 轮
    ...
else:
    return "达到最大轮次，已终止"   # 必须有兜底
```

### 成本控制
- **模型分级**：规划用强模型，简单调用用弱模型
- **缓存**：相同前缀的系统提示/历史命中缓存（prompt caching）
- **流式输出**：改善体验，早失败早止损

## 安全红线

- 工具执行要有**权限白名单**（尤其 shell、文件写入）
- 敏感操作需要**人工确认（human-in-the-loop）**
- 永远不要把 LLM 输出直接当 SQL/命令执行而不校验

## 思考题

1. Agent 执行到一半崩溃了，如何恢复到断点？

### 参考答案

核心思路：**把 messages 的持久化当作"事务日志"，每次变更后落盘，重启时回放。**

**1. 状态快照持久化（基本手段）**
- 每轮循环结束后，把完整 `messages` 写入存储（文件/数据库），带 task_id 和轮次号
- 崩溃恢复 = 读取最近一次快照，直接从下一轮继续，而不是从头重跑
- 关键：**先落盘，再发起下一轮调用**

**2. 工具执行的幂等性（恢复的前提）**
崩溃可能发生在"工具已执行但结果没保存"的瞬间，重跑会有副作用：
- 查询类工具：直接重跑，无害
- 写操作类：带 idempotency key（任务ID+步骤号），重复执行返回同一结果
- 无法幂等的（如发邮件）：先写"即将执行"日志 → 执行 → 写"已完成"日志，恢复时三态判断：
  - 无记录 / 已完成 → 重跑 / 跳过
  - 只有"即将执行" → **人工确认**（无法确定是否执行成功）

**3. 检查点（Checkpoint）**
对多步长任务，每完成一个子目标存一次 checkpoint，恢复时从最近的子目标边界开始，而非任意轮次。

**恢复流程示例：**
```
加载最新快照 → 校验最后一步工具状态 → 幂等补齐未完成步骤 → 继续循环
```
