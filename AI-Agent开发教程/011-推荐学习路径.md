| 步骤 | 产出 | 检验标准 |
|---|---|---|
| 2 | 最小 Agent | 能回答需要查工具的问题 |
| 3 | 多工具 Agent | 能根据问题自动选对工具 |
| 4 | 有记忆的 Agent | 跨轮次不遗忘、能拆解 3 步以上任务 |
| 5 | 框架版 Agent | 能说清框架封装了什么、和手写版的对应关系 |

## 为什么先手写再学框架

- 框架（LangGraph 等）底层就是 010 课那个循环
- 先手写 → 看框架源码秒懂 → 知道什么时候该用框架、什么时候不用
- 避免"框架黑盒"：出了问题只能试参数，不知道底层发生了什么

## 框架速览

| 框架 | 特点 |
|---|---|
| LangGraph | 图状状态机，适合复杂流程控制 |
| OpenAI Agents SDK | 轻量，官方出品，内置 handoff 多智能体 |
| Claude Agent SDK | 深度集成工具/子 Agent/权限控制 |
| (纯手写) | 依赖少、完全可控，简单场景最佳选择 |

### 代码案例：同一个需求的三种写法（对应关系）

```python
# ── ① 纯手写（010 课）：显式循环 ──────────────────────
while True:
    msg = llm(messages, tools)
    if not msg.tool_calls: return msg.content
    messages += execute(msg.tool_calls)

# ── ② OpenAI Agents SDK：框架接管循环 ──────────────────
from agents import Agent, Runner
agent = Agent(name="助手", instructions="...", tools=[get_weather])
result = Runner.run_sync(agent, "北京天气？")   # 循环被封装在 Runner 里

# ── ③ LangGraph：把循环显式画成状态图 ──────────────────
from langgraph.graph import StateGraph, END
g = StateGraph(AgentState)
g.add_node("llm", call_model)          # LLM 决策节点
g.add_node("tools", run_tools)         # 工具执行节点
g.add_edge("llm", "tools")             # 有工具 → 执行
g.add_conditional_edges("llm", lambda s: END if not s["tool_calls"] else "tools")
app = g.compile()                      # checkpointer 参数 = 断点恢复(008课)
```

**对照理解**：
- 手写的 `while` 循环 = LangGraph 的边和条件跳转 = SDK 的 `Runner`
- `messages` = LangGraph 的 State（框架把它变成了可持久化的 state）
- 框架额外给你：checkpoint、并行节点、流式中间态——这些手写要自己造

## 思考题

1. 你的什么需求会需要框架？什么需求手写就够？

### 参考答案

**手写就够（推荐从这里开始）：**
- 工具少（≤5 个）、流程线性的任务（如：查数据 → 格式化 → 输出）
- 个人项目、原型验证、内部小工具
- 对延迟/成本敏感，要精控每一轮调用
- 深度定制需求（特殊消息格式、私有模型协议）
- 判断标准：**一个 while 循环 + 几个 if 能写清的，就不要用框架**

**需要框架的信号：**
- 复杂流程控制：分支、循环、回滚、断点恢复（LangGraph 的状态机价值所在）
- 多 Agent 编排：任务分发、handoff、结果汇总
- 生产化需求：内置 tracing、评估、并发、checkpoint、人机协同审批
- 团队协作：需要统一的抽象和最佳实践，避免每人手写一套
- 长期维护的业务系统（框架 = 别人替你踩过的坑）

**决策流程：**
```
原型阶段：手写（理解底层，需求还没稳定）
   ↓ 需求稳定、复杂度上升
出现"图状状态/多Agent/断点恢复"需求 → 上框架
   ↓
始终简单 → 保持手写，别为用框架而用框架
```

**经验之谈**：手写过一遍 010 课的循环，是判断"这个需求到底要不要框架"的前提——否则你只能盲选。
