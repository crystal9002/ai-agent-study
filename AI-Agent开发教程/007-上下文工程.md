# 007 上下文工程

## 本课要点

比提示词工程更重要：控制"喂什么、何时喂、喂多少"。

- 上下文窗口是稀缺资源
- 只保留当前任务相关的信息
- 关键信息放首尾，中间容易被忽略

## 上下文的组成

```
[系统提示词] + [长期记忆/RAG检索结果] + [对话历史] + [当前任务] + [工具结果]
```

## 核心原则

1. **相关性过滤**：与当前任务无关的历史一律不放
2. **工具结果压缩**：网页全文/文件全文不能直接塞，先截断或摘要
3. **首尾效应**：重要指令放开头（系统提示）和结尾（最后一条消息）
4. **分层加载**：先给概要，需要细节再让 LLM 自己读取（渐进披露）
5. **及时遗忘**：任务完成后，中间过程可以丢弃，只留结论

### 代码案例：工具结果的截断与分层加载

```python
def call_tool(name: str, args: dict, max_chars: int = 4000) -> str:
    """第一道防线：工具层压缩，防止原文撑爆上下文"""
    result = raw_tool_exec(name, args)          # 真实执行
    if len(result) <= max_chars:
        return result
    return (
        result[:max_chars]
        + f"\n...[已截断，共 {len(result)} 字符；"
          f"如需更多内容请带关键词再次调用 {name} 的 offset/keyword 参数]"
    )

# 配合"分层加载"：给日志/文件类工具加二次检索参数
# search_file(path, keyword=None, offset=0, limit=200)
```

### 代码案例：按当前任务过滤历史消息

```python
def build_context(system: str, history: list, current_task: str) -> list:
    """相关性过滤：历史只保留与当前任务同一主题的片段"""
    relevant = [
        m for m in history
        if m["role"] == "system" or any(k in str(m.get("content")) for k in keywords(current_task))
    ][-20:]                                  # 再兜底：最多 20 条
    return [{"role": "system", "content": system}] + relevant + [
        {"role": "user", "content": current_task}   # 当前任务放最后（首尾效应）
    ]
```

## 对比

| | 提示词工程 | 上下文工程 |
|---|---|---|
| 关注 | 措辞、指令格式 | 信息的选择与组织 |
| 层面 | 单次调用 | 整个 Agent 运行时 |
| 典型问题 | "怎么问效果好" | "该给它看什么" |

## 思考题

1. 工具返回了 10 万行日志，你的 Agent 应该怎么办？

### 参考答案

**直接塞进上下文是最差选择**——10 万行远超窗口容量，即使塞得下也会淹没关键信息、推高成本。

正确做法是**分层处理，按需加载**：

1. **在工具层截断**（第一道防线）
   工具返回前就做预处理：只回传前 N 行 + 总行数 + "已截断"提示；或只回传统计摘要（错误类型分布、时间范围）。

2. **让 LLM 自己检索细节**（渐进披露）
   提供 `search_logs(keyword, line_range)` 这类二次检索工具，先给概要，LLM 需要时再精准取片段——这正是文件系统/日志类工具的标准设计。

3. **摘要优先**
   先用 LLM（或规则提取）压缩成"5 条 ERROR 摘要 + 关键时间点"，原始日志留在外部，只在需要时读取。

4. **绝对不要做的**
   - ❌ 原文全量塞进 messages（撑爆窗口、成本失控）
   - ❌ 无脑截断前 100 行就当完整（错误往往在中后段）

**一句话原则：上下文里放"索引和结论"，原文放外面，需要时再取。**
