# 009 评估与观测

## 本课要点

- **轨迹日志（Tracing）**：记录每一步的输入/输出/耗时/成本
- **评估方式**：
  - 端到端：任务成功率
  - 单步：工具选择准确率、输出质量评测
- 没有观测 = 没法迭代优化

## Tracing 的结构

一次 Agent 运行 = 一条 trace，包含多个 span：

```
trace: 用户任务「查北京天气并写进笔记」
 ├─ span: LLM 调用 #1 (选择工具, 1.2s, 800 tokens)
 ├─ span: 工具 get_weather (0.3s)
 ├─ span: LLM 调用 #2 (生成答案, 1.5s, 1200 tokens)
 └─ span: 工具 write_note (0.1s)
 总计: 3.1s, 2000 tokens, $0.01
```

## 必须记录的字段

- 每轮的完整 messages 快照
- 工具入参、返回值、耗时
- token 用量与成本
- 失败原因与重试次数

## 评估方式

| 层级 | 指标 | 方法 |
|---|---|---|
| 端到端 | 任务成功率 | 固定测试集 + 断言（文件是否生成、答案是否正确） |
| 单步 | 工具选择准确率 | 人工标注或 LLM-as-judge |
| 回归 | 新版本是否退化 | 每次改提示词后跑全量测试集 |

## 工具选择

- 轻量：自己打印日志 + JSONL 文件
- 开源：LangSmith、OpenTelemetry + Jaeger、Langfuse

### 代码案例：给 010 课的循环加 Tracing（JSONL 落盘）

```python
import json, time, uuid
from contextlib import contextmanager

TRACE_FILE = "traces.jsonl"

@contextmanager
def span(trace_id: str, kind: str, name: str):
    """计时并记录一个 span：kind = llm | tool"""
    t0, rec = time.time(), {"trace_id": trace_id, "span_id": uuid.uuid4().hex[:8],
                            "kind": kind, "name": name}
    try:
        yield rec
        rec["status"] = "ok"
    except Exception as e:
        rec["status"], rec["error"] = "error", str(e)
        raise
    finally:
        rec["duration_s"] = round(time.time() - t0, 2)
        with open(TRACE_FILE, "a") as f:
            f.write(json.dumps(rec, ensure_ascii=False) + "\n")

# 接入 Agent 循环：
def run_agent_traced(user_input: str, max_turns: int = 10):
    trace_id, messages, cost = uuid.uuid4().hex, [{"role": "user", "content": user_input}], 0.0
    for turn in range(max_turns):
        with span(trace_id, "llm", f"call#{turn}") as s:
            resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
            msg = resp.choices[0].message
            s["tokens"] = resp.usage.total_tokens
            cost += resp.usage.total_tokens / 1e6 * 2.5   # 按单价累计
        messages.append(msg)
        if not msg.tool_calls:
            print(f"[trace {trace_id}] {turn + 1} 轮, ${cost:.4f}")
            return msg.content
        for tc in msg.tool_calls:
            with span(trace_id, "tool", tc.function.name) as s:
                s["args"] = tc.function.arguments
                result = TOOL_REGISTRY[tc.function.name](**json.loads(tc.function.arguments))
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
    return "达到最大轮次"
```

**排查问题时的用法**：

```bash
# 看某次失败 trace 的全部环节
grep '"trace_id": "abc123"' traces.jsonl | jq
# 统计哪类工具最慢 / 最容易出错
jq -s 'group_by(.name) | map({name: .[0].name, avg_s: (map(.duration_s)|add/length)})' traces.jsonl
```

## 思考题

1. 任务失败时，你如何快速定位是"提示词问题"还是"工具问题"？

### 参考答案

方法：**看 trace 的失败点落在哪一层，用"隔离变量"逐步排查。**

**第一步：定位失败环节（看 trace）**

| 失败现象 | 大概率问题层 |
|---|---|
| LLM 选错了工具 / 参数传错 | 提示词问题（工具描述、示例） |
| 工具被正确调用，但返回报错/超时 | 工具问题（代码、依赖、权限） |
| 工具返回正确数据，但最终答案错误 | 提示词问题（没告诉它怎么用结果） |
| 循环空转、反复调同一个工具 | 提示词问题（缺失败处理指引）或工具结果不可用 |

**第二步：隔离验证**
1. **单测工具**：不经过 LLM，直接手动调用工具，传 LLM 用过的同一参数
   - 结果错 → 工具问题
   - 结果对 → 进入第 2 步
2. **回放 trace**：拿记录下来的 messages 原样手动调 LLM（不执行工具）
   - 选择还是错 → 提示词问题
   - 选择对了 → 问题在执行/结果回填环节

**第三步：对照修复**
- 提示词问题 → 改描述、加 few-shot、明确边界（改完跑回归测试集）
- 工具问题 → 修代码；修不了就把错误信息规范回填，让 LLM 能识别并绕过

**关键前提**：009 课讲的 tracing 必须先就位——没有每轮 messages 快照和工具入参/返回值的记录，这个排查根本无从下手。
