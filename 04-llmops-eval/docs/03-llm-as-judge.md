# 03 · LLM-as-Judge：提示词、校准与陷阱

代码：`llmops/judge.py`

## 为什么需要裁判

硬指标只认关键串和子串——"29 元/月"和"每月收费 29 元，年付打 8 折"在 containment 眼里只看有没有"29"，表达质量、逻辑完整性、编造检测全靠人眼。人眼看不过来 50 条 × 每周 N 次的回归，于是用一个 LLM 当裁判（LLM-as-judge）。

本教程裁判评两个维度（`judge.py`）：

- **faithfulness 忠实度**：答案中的事实能否被证据（检索到的 chunk）支持？专抓编造。
- **relevance 相关性**：答案是否正面回应了问题？专抓跑题、答非所问。

## 提示词设计（`JUDGE_SYSTEM` / `FAITHFULNESS_USER`）

四个要素，缺一就会飘：

1. **角色与输出契约**：`只输出一个 JSON 对象，不要输出任何其他文字`，格式写死 `{"score": n, "reason": "..."}`。LLM 对"格式要求"的服从远好于对"评分标准"的服从，所以契约要放最前面、最硬。
2. **证据先行**：忠实度评估把【证据】放在问题和答案**之前**——裁判只需要做"答案的每句话能否在证据里找到出处"的核对，不需要自己的世界知识。这抑制了裁判"我觉得这个常识是对的"的越权。
3. **锚定刻度**：1~5 每一档给具体描述（5=完全忠实；3=部分编造；1=与证据矛盾）。没有锚定的 1~5 分，不同模型、不同时间打出来的分不可比。
4. **温度 0**：`temperature=0.0`，裁判要的就是稳定，不是创意。

## 解析健壮性（`_extract_json` + 重试 + 降级）

裁判也是 LLM，输出不可信。三道防线：

```python
# 1. 正则抠 JSON（容忍 ```json 包裹与前后废话）
m = re.search(r"\{.*?\}", text, re.DOTALL)
# 2. 解析失败自动重试（默认 2 次）
for _ in range(retries + 1): ...
# 3. 仍失败返回 None——评估不中断，聚合时跳过
```

`_extract_json` 还要校验 `score` 是 1~5 的整数——裁判输出 `{"score": "5分"}` 或 `{"score": 9}` 都要判失败重试，**脏分数比缺分数更危险**（缺分被跳过，脏分污染均值）。

`judge_both` 里两个维度任一失败则整体降级 None：与其输出半个结果让下游猜，不如干净地缺席。`judge_coverage` 指标（见 02 课）负责让缺席可见。

## 校准：让裁判对齐人的判断

裁判不是"配好就能信"的，上线前要校准：

1. **人工抽检 30~50 条**：人按同一份刻度打分。
2. **算一致性**：与人分的 Spearman 相关、或"差 ≥2 分"的比例。差 ≥2 分超过 10% 的维度不建议启用。
3. **仲裁 badcase**：人机分歧最大的 10 条逐条看——是裁判刻度理解偏了（改提示词锚定描述），还是人自己打分飘了（统一人工标准）。
4. **定期复校**：换裁判模型、prompt 大改、被评系统大改后都要重来。

## 自偏好偏差（self-preference bias）

两个已知偏差，设计评估时要防：

- **自偏好**：裁判模型倾向给"自己家族/自己风格"的输出打高分。用 deepseek-chat 评 deepseek-chat 生成的答案，分数系统性偏高。对策：裁判与被评**异源**（如 GPT 系裁判 + 国产被评模型），或对版本对比类评估固定裁判模型不变。
- **长度偏好**：裁判天然偏爱长答案。对策：相关性刻度里明确"略冗余"要扣分（本教程 RELEVANCE_USER 里写了"详略得当"）；对长度敏感的场景可加一条"答案超过必要长度 2 倍以上，相关性不得高于 3 分"。

## 代码对应

| 符号 | 职责 |
|------|------|
| `JUDGE_SYSTEM` | 输出契约：只出 JSON、1~5 分 |
| `FAITHFULNESS_USER` / `RELEVANCE_USER` | 证据/问题/答案模板 + 锚定刻度 |
| `_extract_json` | 正则抠 JSON + score 合法性校验 |
| `judge_score` | 重试（默认 2 次）+ 失败降级 None |
| `judge_both` | 两维合评，任一失败整体降级 |

## 生产要点

- **裁判模型独立配置**：`.env` 里 `JUDGE_MODEL` 可与 `LLM_MODEL` 分离——被评模型越换越强，裁判要保持**固定**，否则历史分数不可比。
- **judge 也是成本**：本教程一次 RAG 评估 9 条 qa × 2 次裁判调用 ≈ 18 次 LLM 调用，比被评管线本身还贵。PR 门禁跑硬指标，judge 放夜间/发版任务里。
- **留存裁判理由**：`reasons` 落盘在 cases 明细里，人工复核时不用重跑就能知道裁判为什么打这个分。
- **别用裁判替代人**：发版前 judge 均分达标后，仍要人工看全部"硬指标过但 judge 低分"的交集用例——那是系统性风险高发区。

## 思考题

1. 裁判提示词里把【证据】放在【问题】和【答案】之前，是为了解决什么问题？
2. 为什么 `_extract_json` 要校验 score ∈ [1-5]，而不只是"能 json.loads 就行"？
3. 用被评模型自己当裁判，评估"新 prompt vs 旧 prompt"会有什么隐患？

## 参考答案

1. 抑制裁判越权使用自身世界知识。忠实度核对的本质是"答案内容能否在证据里找到出处"；证据放前面建立"以证据为唯一事实来源"的语境，否则裁判会用常识补全——模型编造了一个符合常识但证据里没有的事实，裁判反而给高分。
2. json.loads 成功只保证"是合法 JSON"，不保证"分数可用"。`{"score": 10}`、`{"score": "五分"}`、`{"score": 3.7}` 若放行，会以字符串/越界值形态进入聚合均值，产生比缺分更隐蔽的污染。合法性校验失败走重试，重试用尽降级 None——宁缺勿脏。
3. 自偏好偏差：模型倾向给同家族输出打高分。如果新旧 prompt 都用同一个模型生成、又用它自己当裁判，新 prompt 的风格变化（比如更接近裁判自己的表达习惯）会获得系统性加分，对比结论失真。对策：裁判异源或至少固定不变，并结合硬指标交叉验证。
