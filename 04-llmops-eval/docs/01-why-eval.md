# 01 · 为什么必须评估

代码：`data/golden_rag.jsonl`、`data/golden_agent.jsonl`、`llmops/runner.py`

## 没有评估的 LLM 开发是什么样

改了一版 prompt，感觉"好像更通顺了"；换了个模型，感觉"好像更快了"——然后上线，投诉率翻倍。

LLM 应用的三个残酷事实决定了**评估不是可选项**：

1. **非确定性**：同一个问题，temperature=0.7 两次答案都可能不同。"我测了几个例子觉得没问题"在统计上不成立。
2. **改动牵一发动全身**：RAG 改检索参数会影响答案、改 prompt 会影响拒答率、换模型会影响工具调用格式。没有基线，你不知道改好了还是改坏了。
3. **退化是无声的**：检索 hit@1 从 0.9 掉到 0.8，端到端通过率可能只掉 2%，肉眼完全看不出；月底一看用户满意度掉了 10 个点，才发现是两周前某次"小改动"。

所以核心问题不是"要不要评估"，而是"**改一版 prompt / 换一个模型 / 调一个参数之后，怎么知道没退化**"——答案是：改前跑一遍 golden set，改后再跑一遍，`scripts/04_report.py` 逐指标对比，下降超阈值标红。这就是本教程的主线。

## Golden Set 设计

Golden set（黄金集/标准答案集）是评估的地基。本教程的两个文件：

- `data/golden_rag.jsonl`：每行一条检索/问答用例
- `data/golden_agent.jsonl`：每行一条 Agent 任务用例

一条 RAG 用例长这样：

```json
{"id": "rag-05", "type": "qa",
 "question": "数据加密采用什么方式？有没有安全认证？",
 "expected_chunks": ["AES-256", "ISO 27001"],
 "expected_answer_contains": ["AES-256"]}
```

`expected_chunks` 判检索层（该召回的资料召回了吗），`expected_answer_contains` 判生成层（答案里关键事实出现了吗）。两层分开打分，badcase 才能归因：**检索没到位调检索，检索到位答错调 prompt**——和 01 RAG 教程"先看检索结果再看回答"的调试心法一脉相承。

### 三类用例都要有

| 类型 | 占比建议 | 例子（本教程 rag-12 / agent-03） |
|------|---------|--------------------------------|
| 正常路径 | ~60% | "团队版多少钱"——高频、典型问法 |
| 边界 | ~25% | 退款规则细节、多约束问题（又问加密又问认证） |
| 对抗 | ~15% | "你们 CEO 是谁"——知识库里没有，**期望拒答**而非编造 |

对抗用例专门测幻觉防线。rag-12 的 `expected_answer_contains: [""]` 就是断言"答案里要出现'没有'这类拒答表述"。忘了放这类用例，你的评估全绿，上线后模型开始自信编造。

### 样本量与分层

- **起步 30~50 条**：太少没统计意义（30 条里对 1 条就是 3.3% 波动），太多维护不动。本教程为了 API 成本控制用 12+8 条演示，真实项目按业务问题类型分层扩充。
- **分层抽样**：按"问题类型 × 难度 × 用户群"切格子，每格至少 2~3 条，避免 50 条全是"查价格"。
- **golden set 是活的**：线上 badcase 定期回流（见 [05 · 回归](05-regression.md)），它才会随着系统一起成长。

## 代码对应

| 文件 | 职责 |
|------|------|
| `data/golden_rag.jsonl` | 12 条 RAG 用例（含 3 条 retrieval 类、1 条对抗拒答） |
| `data/golden_agent.jsonl` | 8 条 Agent 任务用例（必调工具 + 成功断言 + 轮次上限） |
| `llmops/runner.py` | `run_rag_eval` / `run_agent_eval`：逐条执行 + 打分 + 聚合 |

注意 Agent 用例的三个字段：`must_call_tools`（过程断言——不是蒙对答案就算成功，工具得用对）、`success_regex`（结果断言）、`max_turns`（效率约束）。**过程 + 结果 + 成本**三个维度缺一不可：一个绕了 10 轮才答对的 Agent 和 2 轮答对的，线上成本差 5 倍。

## 生产要点

- **数据来源**：真实用户 query 洗出分布 + 人工构造边界/对抗 + PM 给的业务"标准答案"。别只靠 LLM 造用例（会有同源偏差，judge 偏好自己生成的风格）。
- **版本管理**：golden set 进 git（本教程就是），每条用例有稳定 id，改用例单独提交——否则"指标涨了"分不清是系统变好还是考题变简单。
- **脱敏**：从生产日志回流的 query 要脱敏（人名/订单号/手机号）再进 golden set。
- **拒答期望要写对**：对抗用例断言的是"拒答 + 不编造"，不是"必须答出来"，否则等于鼓励幻觉。

## 思考题

1. 为什么 `expected_answer_contains` 不直接用"完整标准答案"做全等比较？
2. golden set 只放"正常路径"用例会漏掉什么风险？
3. Agent 评估为什么必须断言 `must_call_tools`，只看最终答案不行吗？

## 参考答案

1. LLM 表达天然多样化，全等比较会把"换种说法但事实正确"误判为失败，指标虚低、信噪比差。关键串包含 + LLM judge 打分是更稳的组合；需要严格对齐的事实（数字/型号）放进 contains 即可。
2. 拒答能力测不到——模型对知识库没有的问题会编造，正常用例全绿也发现不了；多约束、长问题、口语化指代这些真实分布里的"难例"也会缺席，评估结果虚高。
3. Agent 可能"蒙对"：不调 calculator 直接心算答对 193，这次对了不代表规律；更危险的是用错误工具链碰对答案（比如该 search 的地方 hallucinate 出资料内容）。`must_call_tools` 锁住过程正确性，加上 `max_turns` 锁住效率，才是可上线的断言。
