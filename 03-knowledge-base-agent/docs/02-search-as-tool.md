# 02 · 检索即工具：schema 设计与 prompt 合同

代码：`kba/tools.py`、`kba/kb.py`、`kba/agent.py::SYSTEM`

## 本课要点

- 工具的 **docstring + 类型签名 = 模型看到的 API 文档**，直接决定调用质量
- 返回结构里带 `n`（引用编号），是"证据 → 引用"这条链的**契约**
- 防幻觉靠三层：prompt 合同（必须先查）→ 引用可核验（编号对得上）→ 查不到就明说

## 一、把检索包成工具：`search_kb`

```python
def search_kb(query: str, k: int = 3) -> dict:
    """检索企业知识库（产品手册/价格FAQ/API 文档）。参数：query 自然语言问题，
    k 返回条数（默认 3，上限 10）。返回 results 列表，每项含 n（引用编号）、
    doc（来源文档）、title（章节）、text（片段）。……"""
```

注册表用 `inspect` 读签名自动生成 JSON Schema（同 02 教程 `ToolRegistry`），
模型最终看到的是：

```json
{"type": "function", "function": {
  "name": "search_kb",
  "description": "检索企业知识库…必须基于返回内容…标注来源编号 [1]…",
  "parameters": {"properties": {"query": {"type": "string"},
                                "k": {"type": "integer"}},
                 "required": ["query"]}}}
```

设计要点（每条都踩过坑）：

1. **description 写"何时用 + 怎么用 + 返回什么"**：模型完全靠它决定行为，
   把"回答涉及产品/价格/接口必须基于返回内容"写进工具描述，等于合同签了两次。
2. **参数宽容**：模型会把 `k` 传成 `"5"`，`search_kb` 里 `int(k)` 兜底，
   而不是让它抛 `TypeError` 浪费一轮。
3. **返回结构带 `n`**：`{"n": 1, "doc": "pricing_faq", "title": "版本价格", "text": …}`，
   `n` 就是回答里的 `[1]`。**编号在工具侧生成**，模型只负责引用，不会自己编序号。
4. **返回要"足量但不超载"**：默认 k=3、上限 10，每条截到一个 chunk——塞太多会
   稀释注意力（"迷失在中间"），太少会漏证据。
5. **查不到要有显式信号**：`{"results": [], "note": "知识库中没有相关信息…"}`，
   逼模型把"没有"说出来，而不是硬编。

## 二、prompt 合同：`agent.py::SYSTEM`

工具 schema 管"能不能调"，system prompt 管"必须怎么调、怎么答"：

```
1. 事实类问题必须先调 search_kb，禁止凭记忆编造
2. 引用标注 [n]，编号与 search_kb 返回的 n 一致，并给来源清单
3. results 为空 → 明说"知识库中没有相关信息"
4. 金额/折算调 calc，不心算
5. 要求保存时调 write_note
6. 信息齐了再给结论：中文、直接给答案
```

这六条构成**证据合同**：先检索（来源可靠）→ 标编号（可核验）→ 缺证据如实说
（不编造）→ 关键数字走工具（不心算）。

## 三、防幻觉的三层防线（纵深，而不是指望一句 prompt）

| 层 | 机制 | 失效时的表现 |
|----|------|--------------|
| 1. 行为约束 | `SYSTEM` 规则 1/3，工具 description 复述一遍 | 模型偶尔跳过检索 → 但没有证据就没有 `[n]`，用户易察觉 |
| 2. 可核验 | 回答里 `[n]` ↔ 工具返回的 `n` 一一对应 | 引用对不上 = 幻觉实锤，可做自动化校验（见 [05](05-production.md)） |
| 3. 结构兜底 | 工具错误转 `{"error":…}` 回填、`results: []` 显式空 | 模型看到 error 能换参数自救，看到空结果会改口"知识库没有" |

注意工具**绝不抛异常**：`ToolRegistry.invoke()` 捕获一切异常转结构化错误回填。
异常会打断循环，而错误文本会进上下文，让模型有机会换 query 重查——实测里
`k` 传错类型 → 模型自己改成整数重试成功。

## 思考题

1. 为什么引用编号 `n` 在**工具侧**生成，而不是让模型回答时自己从 [1] 开始数？
2. `k` 的默认值给 3、上限 10，这个区间是检索质量的"召回"还是"精度"在起作用？
3. 把"必须先检索"只写在 system prompt 里、不写进 `search_kb` 的 description，
   会有什么问题？

## 参考答案

1. 模型数序号会漂移：多轮检索后上下文里有多组结果，模型容易张冠李戴。
   由工具为**本次返回**编号，模型只需原样引用，编号 ↔ 证据是机械对应关系，
   也才可被程序自动校验（回答中的 `[n]` 必须存在于最近一次 `search_kb` 结果）。
2. 主要是精度：候选越多、无关片段越多，答案越容易被稀释；本教程语料小，
   k=3 已能覆盖证据。生产上通常"召回求全（top-20~50）+ 重排求准（top-3~5）"，
   见 01 教程 [04 · 召回与重排](../01-rag-knowledge-base-tutorial/docs/04-retrieval-and-rerank.md)。
3. 检索决策是**场景相关**的：同一个工具在"闲聊"里不该被调用。system prompt 面向
   全部对话，description 面向"这个工具是什么"，两处语义侧重不同；只写一处，
   不同模型/不同版本的遵循度会不一致——**关键约束写两遍**是工程上的冗余设计。
