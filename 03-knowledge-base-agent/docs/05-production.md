# 05 · 生产化落地：知识库 Agent 的上线清单

## 本课要点

- 索引是**会过期的资产**：重建/增量策略要先定，否则 Agent 答的是昨天的世界
- 引用不是装饰：`[n]` ↔ chunk 必须可回查，这是审计、评估、纠错的共同地基
- 评估两条腿：**检索命中率**（证据对不对）+ **答案忠实度**（有没有超出证据）
- 多租户场景，权限必须在**检索层**过滤，而不是靠 prompt"别看别人的"

## 架构总览

```
文档源(CMS/Git) ──变更触发──→ 增量/全量重建 ──→ 索引 index/（带版本号）
                                                    │
用户问题 → 会话/权限层（租户、角色）──→ ReAct 循环 ─┤ search_kb（权限过滤后召回）
                                                    │ calc / write_note（审计日志）
                                           生成 → 回答 + [n] 引用
                                                    ↓
                                          评估埋点：召回、忠实度、耗时、token
```

## 1. 索引新鲜度

| 策略 | 做法 | 适用 |
|------|------|------|
| 全量重建 | `scripts/01_build_kb.py` 定时跑（如凌晨），原子替换 `index/` 目录 | 文档 < 万级，最简单可靠 |
| 增量更新 | 按 `doc_id` 只重嵌变化文档，其余向量复用 | 文档大、更新频繁（需把 chunk→向量映射入库，见 01 教程 sqlite 后端） |
| 灰度切换 | 新旧索引并存，检索路由切新版本，出问题秒回滚 | 对可用性敏感的线上服务 |

要点：**重建期间检索不能中断**（双缓冲）；`chunks.json` 里带上 `updated_at`，
让回答能标注"依据 2026-10-19 版价格表"；知识库的"事实变更 → 索引可见"延迟
就是用户感知的**陈旧度 SLO**。

## 2. 引用溯源（把 `[n]` 用起来）

- 落库：每次回答连同 `question / 引用的 chunk_id 列表 / 答案` 一起存，出客诉能复原
  "当时依据的是哪句话"。
- 校验：程序化检查回答里出现的 `[n]` 都存在于最近一次 `search_kb` 返回——
  对不上即判**疑似幻觉**（02 教程 `ToolRegistry` 已保证编号由工具生成，可机械核验）。
- 展示：前端把 `[n]` 做成悬浮卡片显示 chunk 原文（本教程 `web/index.html` 渲染成
  徽标，可再加 `title` 提示）。

## 3. 评估（不做评估 = 盲调）

两条腿分别测，定位问题出在检索还是生成：

1. **检索命中率**（`search_kb` 返回的 top-k 里有没有黄金证据）：
   准备 30~50 条 `(问题, 应命中的 doc/chunk)` 测试对，跑 **Hit Rate@k / MRR**，
   改 `chunk_size`、`k`、召回模式都要重跑——方法与指标定义见 01 教程
   [04 · 召回与重排](../01-rag-knowledge-base-tutorial/docs/04-retrieval-and-rerank.md) 的
   "检索质量评估"一节。
2. **答案忠实度**（回答是否只用了检索到的证据、引用是否对得上）：
   LLM-as-Judge 打分（有据/部分有据/编造）+ 引用编号校验的**确定性断言**；
   Agent 侧再加**工具轨迹断言**（如"价格类问题必须出现 search_kb 调用"），
   任务完成率/工具调用数等指标见 02 教程 [05 · 生产化落地](../../02-agent-tutorial/docs/05-production.md)。

一句话分工：**01 教程管"查得准不准"，02 教程管"做得成不成"，本教程多一条
"引得对不对"**。

## 4. 多租户与权限

- **过滤必须在检索层做**：`search_kb(query, k, tenant_id, roles)` → 召回后按
  chunk 级 ACL 过滤（或建索引时就按租户分 shard），prompt 里写"不要泄露"不算控制。
- 最小权限：工具粒度（某角色只能 `search_kb` + `calc`，没有 `write_note`）；
  `ToolRegistry` 加白名单即可，模型只会拿到它被授权的 `specs()`。
- 审计：谁、何时、以什么参数调了什么工具、返回了多少条 → 全量日志（含写工具落盘路径）。
- 隔离：`index/` 按租户分目录或分库，防止误加载他人索引；缓存 key 必须含租户。

## 5. 上线检查清单

- [ ] 索引重建定时任务 + 双缓冲切换 + 版本号/更新时间可见
- [ ] `max_iters`、单任务 token 预算、工具调用次数上限（原生 `max_iters=6` 是底线）
- [ ] 检索层 ACL 过滤，工具白名单按角色下发
- [ ] 引用编号可回查 chunk 原文；幻觉断言进回归集
- [ ] Hit Rate@k + 忠实度评估跑通，改检索参数必跑
- [ ] 共享资源并发保护（本地 embedding 模型的锁，见 `kba/kb.py::_LOCK`）
- [ ] 错误兜底：工具异常 → `{"error":…}` 回填；服务异常 → 结构化错误事件，不裸抛堆栈
- [ ] 观测：每次 LLM/工具调用打点（耗时、token、参数）

## 思考题

1. 全量重建那 10 分钟里，线上检索应该继续用旧索引还是直接 503？为什么？
2. "价格类问题必须调 search_kb"这类工具轨迹断言，比"答案是否正确"的断言好在哪？
3. 多租户下把租户过滤放在 prompt 里（"你只能看 A 租户的资料"），会有什么实质风险？

## 参考答案

1. 继续用**旧索引**（双缓冲）：知识库少更新 10 分钟的代价远小于服务不可用；
   关键是新索引构建成功后再原子切换，失败则丢弃新目录——绝不能"删了旧的还没建好新的"。
2. 轨迹断言是**确定性的**：不依赖 LLM 打分、可精确断言"未检索却给了价格 = 失败"，
   能把问题归因到"漏检索"这一环；答案正确性断言则受表述差异影响，且答对也可能是
   模型背出来的（正是要防的）。两者互补：轨迹断言进 CI，忠实度打分定期抽样。
3. prompt 不是安全边界：换种问法、长上下文稀释、提示注入都可能让模型越界；
   且没有被检索到的资料根本不会进上下文——**过滤要发生在"进上下文之前"**，
   即检索层/工具层强制执行，prompt 只作为辅助约束。
