# 01 · RAG 原理：为什么需要它

## RAG 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）：在把问题交给大模型之前，先从你自己的知识库中**检索出相关资料**，拼进 Prompt 一起给模型，让模型"看着资料回答"。

```
传统 LLM：  问题 ──────────────────→ LLM → 回答（依赖参数记忆，会编造）
RAG：       问题 → 检索知识库 → 资料+问题 → LLM → 回答（有据可查）
```

## 解决了什么问题

| 痛点 | RAG 如何解决 |
|------|-------------|
| 知识过时 | 模型训练有截止日期，RAG 检索的是**实时更新**的库 |
| 幻觉编造 | 强制"只根据资料回答"，并给出引用，可溯源 |
| 数据私有 | 企业内部文档不可能进训练集，RAG 不需要微调即可接入 |
| 成本高 | 微调一次成本巨大；更新知识只需重新灌库（分钟级） |

> 边界：RAG 擅长"**事实查找型**"问题（价格、流程、参数）；不擅长需要推理建模的问题——那才是微调的领域。两者可叠加。

## 核心架构：两条链路

### 离线索引链路（构建知识库，批处理）

```
文档(PDF/Word/Markdown/网页)
  → 加载与清洗
  → 分块 Chunking          ← rag/chunker.py
  → 向量化 Embedding        ← rag/embedder.py
  → 写入向量库 Vector Store ← rag/vector_store.py
```

### 在线问答链路（用户查询，低延迟）

```
问题
  → 查询向量化
  → 混合召回 top-k（向量 + BM25 → RRF）  ← rag/retriever.py（默认，可关）
  → 重排 rerank top-n（精排，求准确率）  ← rag/reranker.py
  → 拼 Prompt
  → LLM 生成（带引用）                   ← rag/llm.py
```

对应本项目：`rag/pipeline.py` 中 `build_index()` 是离线链路，`query()` / `query_stream()` 是在线链路。

## 关键设计取舍

1. **为什么两阶段检索？** 向量相似度是"双塔"粗比较，快但糙；Cross-Encoder 重排把 query 和文档拼在一起精算，准但慢。所以先用向量海选 50~100 条，再用重排精选 3~5 条。详见 [04](04-retrieval-and-rerank.md)。
2. **为什么 RAG 经常"答非所问"？** 90% 的问题出在**检索质量**而不是 LLM。资料没检索到，Prompt 写得再好也没用——所以本教程把重心放在前四个环节。
3. **上下文窗口越大越好吗？** 不是。塞入无关资料会稀释模型注意力（"迷失在中间"现象），top-n 通常 3~5 足够。
